# EPIC 15 — Authority/AAP Counterparty Mock

## Changes

- _Initial state._

> Part of [Theme 3 — Counterparties](README.md). v0.2 anchors: §4 (role/impersonation matrix).

**AS A** verified partner whose env contains a Gate or a Platform but not an Authority/AAP
**I WANT** the testbed to supply a deterministic, controllable Authority mock
**SO THAT** my partner-supplied component can be probed with realistic authority-side query flows — identifier search, dataset request, follow-up — without my having to also implement and supply an AAP.

**Open:**

- **Authority query corpora** — what queries are issued by default, and how partners can configure their own. AC require configurability, not specific queries.

## Acceptance Criteria

### Protocol coverage

- [ ] The mock exercises the Gate's Authority-facing API (`GET /identifiers/{identifier}`, `GET /dataset/{gateId}/{platformId}/{datasetId}`, `POST /follow-up/...` and equivalents) at the env's selected REST API revision.
- [ ] Authentication mechanism matches the env's declared expectations (TARA OIDC + gate-JWT, X-Road, or alternative — driven by version-matrix selection in Theme 2, E14).
- [ ] The mock supports the legal subset request set per EU Delegated Regulation 2024/2024 at the env's selected XSD version.

### Query semantics

- [ ] Queries cover the documented search dimensions: by UIL, by identifier (vehicle plate + country + date), by other lawful search predicates.
- [ ] Cross-border scenarios are exercisable: a query that requires the partner Gate to fan out to peer Gates (Theme 3, E13) is supported.

### Determinism and scriptability

- [ ] By default the mock issues a documented baseline query mix on Test-Driver instruction. Test runs are reproducible.
- [ ] The Test Driver can script arbitrary query sequences, including: malformed queries, queries with bad credentials, queries that probe permission boundaries, queries with synthetic high-rate bursts (within tier limit, Theme 1 E4).
- [ ] The scripting interface is the same as for Theme 4, E20 (playground) — no second DSL.

### Multi-AAP variants

- [ ] An env may declare multiple Authority-mock instances simulating different authority types (police, customs, transport inspector, etc.), each with its own permission set per the env's permission policy.
- [ ] Each instance has its own credentials minted per E7.

### Resource accounting

- [ ] Authority-mock containers count against env CPU / RAM / storage budgets (Theme 2, E6).

### Marketplace substitution

- [ ] If a marketplace-certified AAP service is selected for this slot (Theme 3, E17), it substitutes for the mock transparently.

### Reporting hooks

- [ ] All query→response pairs generated by the mock are observable to the Test Driver and feed into the Report (Theme 4, E21). The mock does not need to know about reporting; it just runs and is observed.
